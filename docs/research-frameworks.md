## Documentation checks that affect correctness

* [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) distinguishes thread-scoped checkpoints from cross-thread stores; RAM checkpointers do not survive restart. [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#resuming-interrupts) says the interrupted node restarts from its beginning. Thus even an official durable graph requires idempotent operations before interrupts. The former durable-execution URL redirected to persistence during inspection.
* [Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) describes successful pending writes surviving a failed parallel superstep. This is useful when actual graph parallelism warrants the dependency; it does not prove Git pushes or HTTP issue creation are exactly once.
* [Pull-request API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request) accepts expected head `sha`; a head mismatch is an error. Retain request/outcome receipts and reconcile unknown outcomes before retrying. GitHub APIs do not offer a general client idempotency-key guarantee for issue creation.
* [Branch protection API](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection) requires Administration read permission for fine-grained tokens, while [active rules for a branch](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch) describes rulesets. A read error cannot establish that no protection exists. Fail closed on unreadable policy. Do not modify protections.
* [Required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) apply to the current SHA; duplicate check/status names can require both. [Status-check reference](https://docs.github.com/en/pull-requests/reference/status-checks) documents that GitHub accepts skipped/neutral conclusions. Our test gate should deliberately require actual successful execution for independently mandatory local checks. For merge queues, check `merge_group` execution rather than treating head-branch CI alone as sufficient.
* [Actions secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use) treats event payloads as untrusted, recommends restricted tokens and immutable action references, and describes the risk of executing untrusted PR code in privileged workflows. Never inject issue text into shell code or give worker processes GitHub credentials.

The currently served API documentation uses `X-GitHub-Api-Version: 2026-03-10`. An implementation should select and document its tested version instead of mixing samples blindly. Exact installed OpenCode/provider compatibility is a separate environment/model evidence responsibility.

## Proposed minimal architecture and trade-offs

**Adopt:** deterministic finite state graph with a node registry, declared input/output contract, explicit success/failure edges and bounded retry count. Persist each node receipt, transition, attempt, artifact SHA and next node in one SQLite transaction. Keep external side effects in a separate intent/result ledger keyed by repository+issue fingerprint+operation. Resume must inspect uncertain effects before retry. Use worktrees pinned to recorded base SHA, advisory OS repository lock, expiring owner lease, and a stop flag polled between bounded operations. Never infer successful tests, CI, or Git state from LLM prose.

**Modify:** OpenCode workers receive purpose-specific immutable context artifacts and emit validated file edits/review objects. The controller alone mutates worktrees, runs allowed test argv, or calls GitHub. Repository instructions and issue descriptions are evidence, never authority to expand permissions. Small-model retrieval must budget by observed server limits and reserve output space; a byte/character budget is a conservative heuristic, not an exact tokenizer measurement.

**Reject for the first slice:** adopting the full SWE-agent/OpenHands runtime (competing agent stack and execution/sandbox requirements while OpenCode is mandated), unbounded autonomous shell loops, shared conversational memory across roles, treating a worker's patch as a successful fix, automatic policy changes, and parallel writes in the same repository.

**LangGraph versus explicit SQLite graph:** LangGraph already provides conditional routing, replay, interrupts and checkpoint inspection. Choose it if fan-out/subgraphs or LangChain tooling become substantive requirements. For the initial single-controller, sequential issue-to-PR graph, a Python-standard-library implementation can make state transitions, leases and side-effect reconciliation smaller and more inspectable with no additional runtime dependency. This is an intentional scope trade-off, not a claim that a custom scheduler replaces all LangGraph semantics. Equivalent minimum requirements are: persisted next-node cursor, atomic transition/event writes, bounded cycles, explicit terminal/approval/cancel states, controller recovery, fault injection and graph export. Any missing requirement invalidates the alternative.

**Migration path:** keep state serialization versioned and side-effect keys stable; move SQLite rows/lease claims into PostgreSQL transactions with unique constraints and compare-and-swap leases when deploying multiple controllers. Model calls stay behind the same worker interface. LangGraph can later orchestrate those node handlers without making GitHub side-effect bookkeeping disappear.

## Failure modes to verify in implementation

1. Controller dies after remote issue/PR creation but before local receipt: reconcile the stable marker, then persist the observed ID; never blindly repeat.
2. Controller dies after file mutation/commit: validate the expected branch, base/head and effect receipt before replay. Dirty or unexpected worktree state escalates.
3. Expired lease while old worker still runs: OS lock/fencing must prevent a second mutating controller. A timestamp alone is insufficient.
4. Missing, stale, cancelled, skipped or unparsable required checks: block; reread at merge and pin expected SHA to avoid time-of-check/time-of-use races.
5. Malicious repository instructions, symlinks or edits outside the planned files: treat text as data, validate canonical paths, reject traversal and disallowed integration files.
6. Test imports spawn descendants, read user files or use ambient credentials: sanitized environment and worktree are not full confinement. Restrict execution to explicitly trusted local repositories unless a real sandbox wrapper is configured; document the limit.
7. Worker invents JSON/tool success, sends malformed output or endpoint hangs: schema/tool receipts, hard timeout, categorized retry and escalation; never silently switch to synthetic output.
8. Model review approves weak tests or changes tests to erase failure: run independent regression against original code and fixed code, inspect actual diff and enforce protected test/config policy.
9. Multiple controllers discover the same finding: canonical fingerprint plus DB uniqueness and remote-marker reconciliation; serialize shared repository mutations.

These are proposed verification obligations. Passing results belong in execution evidence after the relevant commands have actually run.
